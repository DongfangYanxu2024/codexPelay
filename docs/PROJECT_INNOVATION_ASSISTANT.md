# 项目创新助手技术手册

> 文档状态：v0.1（可实现基线）
> 适用对象：产品负责人、项目发起人、Codex Skill 作者、Python 脚本维护者与评审人员
> Skill 入口：`skill/project-innovation-assistant/SKILL.md`
> 确定性脚本：`skill/project-innovation-assistant/scripts/innovation_assistant.py`

## 1. 项目概述

项目创新助手（Project Innovation Assistant，下文简称 PIA）把一段自然语言需求转化为一条可审计的项目决策链：理解需求、发散候选、硬约束过滤、统一评分、两轮自我优化、选择最佳方案、实现最小可行版本（MVP），再依据真实指标评估并迭代。

它不是单纯的“点子生成器”。系统必须同时回答四个问题：

1. 为什么生成这些方案；
2. 为什么某个方案胜出；
3. 胜出方案如何被实现和验证；
4. 指标不达标时应继续、调整、转向还是停止。

### 1.1 核心目标

- 从用户需求中提取目标用户、问题、期望结果、资源边界和成功指标。
- 默认生成**恰好 20 个**候选，固定为 **4 个探索组，每组 5 个**。
- 在评分前执行硬约束校验；不允许用高创意分抵消违法、超预算或不可交付等硬性失败。
- 使用公开权重、证据、置信度、风险和相似度惩罚产生可追溯排序。
- 默认执行**恰好两轮成功的自我优化**，然后从合格方案中选出一个最佳方案。
- 对胜出方案给出可执行的 MVP 计划、验收标准、实验设计和指标方案。
- 当用户请求完整交付时，进入实现、测量和迭代闭环。
- 同一套协议同时支持 Codex Skill 交互模式和本地 Python 脚本模式。

### 1.2 非目标

- 不承诺创意在市场上必然成功，也不把模型判断伪装为用户研究或统计证据。
- 不在没有用户授权时部署、付费、创建外部账号、联系真实用户或执行不可逆操作。
- 不替代法律、医疗、财务、安全与合规专业审查。
- 不自动抓取登录态、浏览器 Cookie 或调用未记录的 ChatGPT Web 接口。
- 不让排序脚本“创作”项目。创意、语义判断和证据解释由模型或人完成；脚本只做结构校验、确定性计算和结果落盘。
- 不为满足数量而复制、轻微改名或填充明显无价值的候选。

### 1.3 规范用语

本文中的“必须”表示协议或验收要求，“应该”表示推荐默认，“可以”表示可选扩展。

## 2. 典型用户场景

### 2.1 从模糊需求得到最佳项目

用户输入“为独立开发者设计一个能减少项目烂尾的工具”。PIA 先形成结构化 brief，记录必要假设；随后按四个探索方向各生成五项，共二十项。系统完成硬约束检查、评分和两轮优化，最终输出一个胜出项目及其 MVP、指标和停止条件。

### 2.2 在明确约束下做内部选型

用户要求“两周内、两名工程师、只能使用本地数据、不得新增付费服务”。PIA 将这些条件写入 `hard_constraints`。违反任一条件的候选仍可保留在审计记录中，但必须标记为不合格，不能进入胜出候选集合。

### 2.3 对已有候选做确定性排序

用户或团队已准备二十个候选。脚本模式读取 `brief.json` 与 `candidates.json`，检查 20 项及 4×5 分组不变量，计算统一得分、惩罚项和排名，生成机器可读的 `decision.json` 与便于评审的 Markdown 报告。

### 2.4 实现后决定下一步

胜出方案已完成 MVP。用户提供转化率、任务成功率、耗时、成本等实测值。PIA 对照目标值和护栏指标给出 `keep`、`iterate`、`pivot` 或 `stop` 建议，并说明证据、差距和下一轮的最小变更。

## 3. 产品边界与运行模式

PIA 有两种互补入口，不是两个互相竞争的实现。

| 模式 | 适用情况 | 负责内容 | 不负责内容 |
| --- | --- | --- | --- |
| Skill 模式 | 用户以自然语言请求发散、选型、验证、实现或迭代 | 语义理解、生成创意、质疑假设、组织两轮优化、调用脚本、解释结果、按授权实现 | 不应自行发明实测数据，不应绕过硬约束或脚本校验 |
| 脚本模式 | CI、本地复现、团队评审、批处理 | 初始化协议文件、校验基数与字段、确定性评分、排序、相似度处理、评估建议、生成审计产物 | 不生成高质量创意，不判断未经结构化的复杂业务语义 |

推荐工作方式是“Skill 编排 + 脚本裁判”：模型产生丰富语义，脚本保证同一输入、权重和参数得到可复现结果。

## 5. 默认契约与不变量

以下值构成 v0.1 的默认决策契约：

| 项目 | 默认值 | 规则 |
| --- | --- | --- |
| 候选总数 | 20 | 必须恰好为 20；19 或 21 都是协议错误。 |
| 探索组 | 4 | 固定为 G1、G2、G3、G4。 |
| 每组候选数 | 5 | 每组恰好 5 个，不能用 6/4/5/5 代替。 |
| 方案优化轮次 | 2 | 默认必须完成两轮成功优化后才选择 winner。 |
| 评分范围 | 每维 0～10 | 超出范围或非数值为协议错误。 |
| 置信度范围 | 0～1 | 表示当前证据下的判断可靠程度，不等于成功概率。 |
| 风险范围 | 0～10 | 越高风险越大。 |
| 实施评估轮次 | 最多 3 | 与前述两轮方案优化不同，可由 brief 显式调整。 |
| 输出 winner | 0 或 1 个 | 正常完成时恰好 1 个；无合格项时为 0，并返回阻塞原因。 |

“生成恰好 20 个”与“合格候选数量”是两个概念。系统始终保留完整的二十项审计集合；硬约束失败项标记为 `eligible: false`。如果二十项全部不合格，正确行为是停止并请求调整需求或资源，而不是让一个不合格项获胜。

## 6. 需求结构化与硬约束

### 6.1 Brief 形成规则

模型应先把输入转为以下信息：

- 原始需求：尽量保留用户原意，不擅自扩大范围；
- 目标：期望改变的用户行为或业务结果；
- 目标用户：谁有问题、谁使用、谁付费或批准；
- 硬约束：任何不可违反的边界；
- 软偏好：可以通过评分体现的取舍；
- 成功指标：主指标、护栏指标、基线、目标值和观察窗口；
- 假设：尚未确认、但为继续工作而暂定的判断；
- 实现授权：只做方案，还是包含实现与验证。

如果用户没有提供量化目标，系统应该提出合理但显式的暂定值，并在报告中标记为“待确认”，不能把它描述为用户承诺。

### 6.2 硬约束分类

硬约束至少覆盖下列类别：

- 时间：截止日期、MVP 周期、可用工时；
- 成本：一次性预算、持续成本、付费服务限制；
- 人力与技能：团队规模、语言栈、维护能力；
- 平台与依赖：操作系统、离线要求、允许的 API；
- 数据：可用性、驻留、隐私、许可与保留期限；
- 安全与合规：行业规则、年龄限制、访问控制；
- 交付：必须产物、可用性、性能或兼容性下限；
- 禁止项：用户明确排除的业务模式、技术或行为。

### 6.3 门禁语义

每个候选的 `constraint_checks` 应逐项记录布尔结果和简短理由。门禁规则如下：

1. 所有适用硬约束都通过，候选才是 `eligible`；
2. `unknown` 不能默认视为通过。关键约束证据未知时，应失败或要求确认；
3. 任何评分维度、证据加分或战略价值都不能覆盖门禁失败；
4. 淘汰项保留在报告中，以便发现需求过紧或生成偏差；
5. 修复失败项时必须形成新版本并记录 lineage，不得改写历史记录。

交互报告可以使用 `pass`、`fail`、`unknown` 三态；脚本输入的 `constraint_checks` 只接受布尔值。`pass` 编码为 `true`，`fail` 编码为 `false`，`unknown` 则不填写对应键，排序输出会记录 `hard_constraint_unverified:<id>`。

## 7. 二十候选生成策略

### 7.1 四个探索组

四组从不同风险与杠杆角度覆盖解空间，避免生成二十个同质化应用：

| 组 | 方向 | 生成要求 |
| --- | --- | --- |
| G1 直接低假设解法 | 直接解决用户陈述的核心问题 | 5 个范围小、路径清晰、可快速验证的候选 |
| G2 邻接与流程解法 | 从端到端流程消除根因、重复劳动或协作摩擦 | 5 个体现效率、质量或可观测性杠杆的候选 |
| G3 进取与技术差异化 | 使用更有野心的机制或技术形成实质差异 | 5 个高潜力、关键假设清楚且仍可测试的候选 |
| G4 约束重构与极简解法 | 重新解释约束，寻找低成本或出人意料的简单路径 | 5 个失败成本可控、能快速获得信息的候选 |

组名表示探索视角，不直接带来加分。G4 不因“更创新”自动胜过 G1，G1 也不因“更稳妥”自动胜过其他组。

### 7.2 单个候选的最小内容

每项候选至少回答：

- 为谁解决什么问题；
- 核心价值和差异点是什么；
- 最小交付物是什么；
- 依赖哪些数据、系统、人员或权限；
- 最大的不确定性和风险是什么；
- 如何在短周期内证伪或验证；
- 六个评分维度及理由；
- 每项硬约束是否通过。

### 7.3 多样性与去重

候选不应只更换名称。若两项的目标用户、核心问题、主要机制和交付物高度相同，应视为近重复。处理顺序为：

1. 在同一组中优先保留硬约束通过、证据更强且可测试性更高的一项；
2. 用该组的新机制候选一对一替换重复项；
3. 保持总数 20、每组 5；
4. 保存被替换项、相似度、替换理由和新候选 lineage；
5. 若无法生成非重复的有效替代项，标记运行阻塞，不能填充空洞方案。

## 8. 评分模型与防偏差机制

### 8.1 六维评分

每维使用 0～10 分，并在 `brief.weights` 中公开权重。默认权重如下：

| 维度 | 字段 | 默认权重 | 10 分含义 |
| --- | --- | ---: | --- |
| 用户吸引力 | `desirability` | 0.25 | 问题重要、目标用户明确，价值主张有直接证据支持 |
| 技术与交付可行性 | `feasibility` | 0.20 | 可在资源与时间边界内实现，关键依赖可用 |
| 持续可行性 | `viability` | 0.15 | 成本、运营、维护或商业逻辑可持续 |
| 创新性 | `innovation` | 0.15 | 不是表面改名，有清楚的新机制或有价值的组合 |
| 战略匹配 | `strategic_fit` | 0.15 | 与用户目标、团队能力和长期方向一致 |
| 可测试性 | `testability` | 0.10 | 能以低成本、短周期和明确指标验证核心假设 |

权重必须均为非负数，并归一化为总和 1。用户可以显式调整权重；调整值和原因必须写入 brief，不能为了让预先偏爱的候选获胜而事后改权重。

脚本把六维加权结果转换为 0～100 的基础分：

```text
base_score = 10 × Σ(normalized_weight[dimension] × score[dimension])

confidence_adjustment = (confidence - 0.5) × 10
evidence_adjustment = -1                         # 没有证据
                    或 min(unique_evidence, 3) × 0.75
risk_penalty = risk × 1.5
similarity_penalty = max(0, (max_jaccard - 0.65) × 20)
duplicate_penalty = 15                           # 摘要规范化后完全相同
                    或 0

final_score = clamp(
  base_score + confidence_adjustment + evidence_adjustment
  - risk_penalty - similarity_penalty - duplicate_penalty,
  0,
  100
)
```

`base_score` 和 `final_score` 的范围为 0～100。脚本把所有组件写入 `score_breakdown`；报告必须逐项列出，禁止只暴露一个不可解释的 `final_score`。公式用于可复现排序，不代表证据真实或因果关系成立。

### 8.2 证据与置信度

证据分为三类：

- `observed`：本项目真实用户、日志或实验的观测；
- `external`：有可核查来源的外部资料；
- `inferred`：从已知事实推导，必须写清推导链；
- `assumed`：尚未验证的工作假设。

空证据、高比例假设或低置信度不得加分。模型不得伪造访谈、市场规模、指标或引用。需要外部事实时，应提供来源或明确标记为待验证。

### 8.3 风险和相似度惩罚

- `risk` 表示交付、采用、数据、安全、合规和运营风险的综合暴露；
- 相似度惩罚用于降低近重复候选在 Top 5 中占据多个位置的机会；
- 惩罚必须是公开、确定且可复现的；
- 惩罚改变排序，但不能改变硬约束门禁结果；
- 风险高但信息增益大的实验仍可以保留，只要其硬约束通过且失败成本受控。

### 8.4 防偏差清单

每次排序至少执行以下控制：

1. **位置偏差**：评分时不因候选出现在列表前部而加分；需要随机顺序时使用记录在案的固定 seed。
2. **组别偏差**：组别不进入评分公式，四组均有被选中的机会。
3. **表达偏差**：评分针对问题、机制、证据和实验，不针对文案华丽程度。
4. **新奇偏差**：创新性仅占 15%，不得压倒吸引力与可行性。
5. **确认偏差**：Round 1 对 Top 5 强制执行反方审查，主动寻找失败证据。
6. **单一指标偏差**：同时使用主指标和护栏指标，防止以转化率换取隐私、质量或成本恶化。
7. **证据偏差**：置信度与证据类型单独记录，模型主观分数不能被当作事实。
8. **重复偏差**：近重复项不能以数量优势挤占 Top 5。
9. **事后调参偏差**：评分后修改权重必须新建决策版本并说明原因。
10. **自动化偏差**：脚本结果是决策辅助；报告应保留用户覆写入口和覆写理由。

## 9. 两轮自我优化

“两轮优化”发生在实现前，目标是提高候选质量和选择可信度；它与实现后的最多三轮指标迭代不同。

### 9.1 Round 0：初始基线

Round 0 产生恰好二十项基线候选，完成首次约束检查和评分，但不立即宣布 winner。它负责建立后续可比较的基线快照。

### 9.2 Round 1：覆盖、约束与反方审查

Round 1 必须执行：

- 检查 4×5 完整性和跨组覆盖；
- 识别近重复并一对一替换；
- 修复可以修复的硬约束失败，同时保留原版本；
- 对初始 Top 5 逐一写“最可能失败的原因”和“什么证据会推翻当前评分”；
- 校正没有证据支持的高分、隐含依赖和过度乐观工期；
- 再次对全部二十项评分。

本轮结束仍必须有恰好二十项、每组五项。任何修改项都记录 `parent_id`、轮次和修改理由。

### 9.3 Round 2：实验化与落地压力测试

Round 2 必须执行：

- 为当前 Top 3 定义最小可验证实验、主指标、护栏指标、目标值和观察窗口；
- 估算 MVP 范围、关键依赖、失败成本和回滚方式；
- 使用新增的可测试性与可行性信息重新评分；
- 再次检查 Top 5 的多样性与硬约束；
- 生成最终完整排名并选择一个 winner。

Round 2 不允许只优化文案。没有改变假设、范围、证据、风险或实验设计的“润色”不算有效优化。

### 9.4 方案阶段停止条件

默认停止规则必须同时可审计：

- **正常停止**：Round 1 和 Round 2 均成功完成，存在至少一个合格候选，且不存在未解决的关键约束未知项；若最高项低于 `minimum_rank_score`，脚本仍会返回当前最优的临时 winner，但 Skill 必须将其标为低质量门禁并在实现前选择继续研究或 pivot；
- **数量阻塞**：任一成功轮次不是恰好 20 项或不是 4×5，停止且不选择 winner；
- **门禁阻塞**：没有合格候选，停止并列出需要放宽或澄清的约束；
- **证据阻塞**：Top 3 的关键事实无法验证，且不同假设会改变 winner，停止并请求信息；
- **安全停止**：继续会造成未授权、高风险或不可逆外部操作；
- **轮次上限**：默认两轮后停止优化，不能因“不够满意”悄悄开启第三轮。

即使 Round 1 分数已经收敛，默认仍要完成 Round 2 的实验化压力测试。只有协议错误、安全问题或缺失的关键用户信息可以提前中断；被中断的运行不得声称已完成两轮优化。

## 10. 最佳方案选择

### 10.1 选择条件

winner 必须满足：

- `eligible` 为真；
- 完成 Round 2；
- 优先达到 brief 中的 `minimum_rank_score`；低于该值时只能作为临时最优项，不能标为已验证方案；
- 关键证据和假设已在报告中公开；
- MVP 能在硬约束内交付；
- 有可运行的验证实验和明确停止条件。

### 10.2 排序与平局

脚本使用未舍入的内部数值计算组件，并按已写入结果的确定性键排序：

1. 合格项先于不合格项；
2. `final_score` 降序；
3. `base_score` 降序；
4. 规范化名称字典序；
5. 规范化候选 ID 字典序；
6. 原候选 ID 字典序。

脚本把组件舍入到四位小数后输出，并按上述稳定规则产生相同顺序。若业务上不能接受机械平局规则，允许用户覆写 winner，但必须保存原排名、覆写对象和理由。

### 10.3 决策包

最终决策包至少包含：

- 原始需求与结构化 brief；
- 二十项最终候选及所有不合格原因；
- 六维分数、基础分、所有调整项与最终分；
- Round 1/2 的变更日志；
- Top 5 反方审查；
- Top 3 实验卡；
- winner 及“为什么胜出/为什么其余 Top 3 未胜出”；
- MVP 计划、指标、风险、回滚和实施授权状态。

## 11. 实现流程

若用户只要求创意或选型，流程在决策包处结束。只有用户原请求明确包含“实现/构建/落地”，或用户随后确认实现时，才进入以下阶段。

### 11.1 实现前检查

1. 检查真实仓库、运行环境和已有改动；
2. 将 winner 的假设映射到可交付的 MVP 范围；
3. 明确不做事项，避免把实验原型扩张为完整平台；
4. 定义验收测试和基线测量方法；
5. 标记需要账号、凭据、付费、生产访问或外部沟通的步骤；
6. 对不可逆或超出授权的动作暂停并请求用户决定。

### 11.2 MVP 实施顺序

```text
winner 决策
  -> 技术切片与任务依赖
  -> 最小端到端路径
  -> 单元/协议测试
  -> 真实或可接受的沙盒验证
  -> 指标采集
  -> 验收报告
```

推荐先实现一条端到端主路径，再补异常处理和可观测性。每个任务应关联一个需求、一个验收条件和一个验证命令。模型不得把未执行的测试描述成“已通过”。

### 11.3 实现交付物

- 代码或可执行原型；
- 配置与最小运行说明；
- 自动化测试及测试结果；
- MVP 范围与已知限制；
- 指标采集说明；
- 风险、回滚和待确认事项；
- 与 winner 决策的追溯链接。

## 12. 评估与实施后迭代

### 12.1 指标设计

每个实验至少包含：

- 主指标：最直接反映目标结果；
- 护栏指标：防止性能、质量、成本、安全或用户体验恶化；
- `direction`：`maximize` 或 `minimize`；
- 基线与目标值；
- 数据来源和测量窗口；
- 最小样本或完成判据；
- 指标负责人（如适用）。

### 12.2 决策状态

| 状态 | 含义 | 典型条件 |
| --- | --- | --- |
| `keep` | 保留当前实现并进入常规维护或扩大验证 | 主指标达标，护栏无明显恶化 |
| `iterate` | 核心假设仍成立，用最小变更继续验证 | 接近目标、问题可定位、继续成本可控 |
| `pivot` | 当前机制未获支持，但问题和用户需求仍成立 | 主指标持续偏离，替代机制有明确证据 |
| `stop` | 停止投入并保存结论 | 目标已完成、硬约束失败、风险不可接受或继续无信息增益 |

### 12.3 实施后停止条件

默认最多进行三轮实施评估。满足任一条件时停止：

- `stop_on_target` 开启且所有主目标达到，护栏指标通过；
- 达到 `evaluation.max_iterations`；
- 连续两轮对主指标没有达到预先约定的最小改善；
- 继续成本超过预算或截止时间；
- 硬约束、安全、隐私或合规条件失败；
- 数据质量不足以支持结论，且无法在边界内修复；
- 用户要求停止。

每轮只应改变最少的一组关键变量，以便把结果归因到具体假设。`evaluate` 的建议是决策辅助；涉及重大投入、外部用户或生产变更时仍由用户批准。

## 13. 系统架构

```text
自然语言需求
     |
     v
Brief Normalizer ----> Assumption / Constraint Ledger
     |
     v
4x5 Candidate Generator (Skill / model)
     |
     v
Hard Constraint Gate ----> Ineligible audit records
     |
     v
Deterministic Ranker (script)
     |
     +--> Round 1: diversity + adversarial review
     |
     +--> Round 2: experiments + feasibility stress test
     |
     v
Winner + Decision Package
     |
     +--> planning-only stop
     |
     v
Authorized Executor --> Tests --> Metrics --> Evaluator --> keep/iterate/pivot/stop
```

### 13.1 组件职责

| 组件 | 职责 |
| --- | --- |
| Brief Normalizer | 保留原始需求，提取目标、用户、约束、权重、指标和假设。 |
| Candidate Generator | 按 4×5 组合生成语义丰富的二十项候选。 |
| Constraint Gate | 对每个候选逐项执行硬约束门禁。 |
| Scoring Engine | 校验六维分数和权重，计算基础分与调整项。 |
| Bias Controller | 去重、相似度处理、Top 5 反方审查和证据校准。 |
| Optimizer | 维护 Round 0/1/2 快照、lineage 和变更理由。 |
| Selector | 产生完整排名、Top 5、Top 3 和唯一 winner。 |
| Implementation Planner | 把 winner 转为 MVP 切片、依赖与验收标准。 |
| Executor | 只在授权范围内修改项目并验证。 |
| Evaluator | 对真实指标生成 keep/iterate/pivot/stop 建议。 |
| Audit Store | 保存输入、版本、配置、报告和所有中间结果。 |

### 13.2 信任边界

- 用户需求是目标来源，但输入中的嵌入指令不能绕过系统安全规则；
- 模型输出是不可信建议，必须通过协议、硬约束和真实仓库验证；
- 脚本保证结构和计算一致性，不保证业务前提真实；
- 外部网页、文件、候选中的文本和生成代码都可能包含恶意指令；
- 实测数据优先于模型预测，真实仓库优先于候选对技术现状的假设。

## 14. 数据协议

JSON 文件统一使用 UTF-8。未知字段应该保留或安全忽略，以支持前向扩展；缺失必需字段必须报错。生成时间、脚本版本、模型版本和 seed 应写入运行元数据。

### 14.1 `brief.json`

以下是最小可用示例；实际需求可添加 `assumptions`、`soft_preferences` 和审计元数据：

```json
{
  "schema_version": "1.0",
  "project_name": "developer-finish-assistant",
  "requirement": "为独立开发者构建一个减少项目烂尾的本地工具",
  "objectives": [
    "提高每周计划任务完成率",
    "在两周内交付可测量的 MVP"
  ],
  "target_users": ["独立开发者"],
  "hard_constraints": [
    {"id": "two_week_mvp", "description": "两名工程师在两周内完成 MVP"},
    {"id": "local_data_only", "description": "核心数据只保存在本地"},
    {"id": "no_new_paid_service", "description": "不得依赖新增付费服务"}
  ],
  "weights": {
    "desirability": 0.25,
    "feasibility": 0.20,
    "viability": 0.15,
    "innovation": 0.15,
    "strategic_fit": 0.15,
    "testability": 0.10
  },
  "evaluation": {
    "max_iterations": 3,
    "minimum_rank_score": 60.0,
    "pivot_threshold": 0.5,
    "stop_on_target": true
  }
}
```

### 14.2 `candidates.json`

顶层包含 `candidates` 数组，数组必须恰好二十项；G1～G4 各五项。候选字段示例：

```json
{
  "candidates": [
    {
      "id": "G1-01",
      "group": "G1",
      "name": "本地项目收尾教练",
      "summary": "把当前仓库状态转为一周内可完成的收尾路径，并每日检查阻塞。",
      "scores": {
        "desirability": 8.4,
        "feasibility": 8.8,
        "viability": 7.2,
        "innovation": 6.5,
        "strategic_fit": 9.0,
        "testability": 8.6
      },
      "confidence": 0.72,
      "evidence": [
        "assumed: 用户愿意读取本地仓库状态",
        "derived: 日任务可直接映射到提交与测试结果"
      ],
      "risk": 3.2,
      "constraint_checks": {
        "two_week_mvp": true,
        "local_data_only": true,
        "no_new_paid_service": true
      },
      "round": 2,
      "lineage": ["G1-01@round0", "G1-01@round1"],
      "change_reason": "缩小范围并补充可验证的完成率指标"
    }
  ]
}
```

`round`、`parent_id` 和 `change_reason` 用于跨轮次追溯；若脚本不参与保存历史，可将每轮完整文件单独落盘，并在运行清单中关联。

### 14.3 `decision.json`

排序输出至少应包含：

```json
{
  "schema_version": "1.0",
  "status": "winner_selected",
  "brief": {"requirement": "...", "weights": {}, "evaluation": {}},
  "ranking": [
    {
      "id": "G1-01",
      "group": "G1",
      "name": "本地项目收尾教练",
      "eligible": true,
      "elimination_reasons": [],
      "rank": 1,
      "score_breakdown": {
        "base_score": 81.25,
        "confidence_adjustment": 2.2,
        "evidence_adjustment": 1.5,
        "risk_penalty": 4.8,
        "similarity_penalty": 0.0,
        "duplicate_penalty": 0.0,
        "raw_score": 80.15,
        "final_score": 80.15
      },
      "similarity": {
        "duplicate_of": null,
        "max_jaccard": 0.21,
        "most_similar_candidate_id": "G2-03"
      }
    }
  ],
  "top5": [{"id": "G1-01", "rank": 1}],
  "winner": {"id": "G1-01", "rank": 1},
  "ranking_rules": {"groups": {"G1": 5, "G2": 5, "G3": 5, "G4": 5}}
}
```

为缩短示例，`brief`、`top5`、`winner` 和 `ranking_rules` 中的对象被省略；真实脚本会写入完整对象。示例数字仅说明字段关系，不能代替脚本实际计算。`ranking` 必须保留全部二十项，包括不合格项；不合格项应包含 `elimination_reasons`。

### 14.4 `metrics.json`

评估输入可以是指标数组，或包含 `metrics` 的对象。每项至少需要 `name`、`value`、`direction` 和 `target`，建议提供 `baseline`：

```json
{
  "iteration": 1,
  "metrics": [
    {
      "name": "weekly_completion_rate",
      "value": 0.61,
      "baseline": 0.38,
      "target": 0.60,
      "direction": "maximize"
    },
    {
      "name": "weekly_manual_minutes",
      "value": 24,
      "baseline": 20,
      "target": 30,
      "direction": "minimize"
    }
  ]
}
```

### 14.5 `iteration.json`

评估输出至少记录当前轮次、逐指标差距、总体建议、理由、下一实验和停止条件状态。传入历史时，不应覆盖旧轮次；应形成可追加或可关联的审计链。

## 15. Skill 模式

### 15.1 触发条件

Skill 应在用户请求包含以下组合任务时触发：

- 根据需求发散并筛选项目；
- 比较多个方向并选出最值得做的一项；
- 对项目创意做验证、实现和指标迭代；
- 明确要求“20 个候选”“自我优化”或“项目创新助手”。

以下情况通常不触发：普通单一功能实现、只要几个随意点子的轻量头脑风暴、与项目决策无关的问答。

### 15.2 Skill 工作流

1. 读取用户需求并建立 brief；
2. 生成四组各五项；
3. 使用脚本校验基数、约束、权重与排名；
4. 执行 Round 1，保存反方审查和变更；
5. 执行 Round 2，保存 Top 3 实验并重排；
6. 解释 winner 与关键权衡；
7. 根据用户原始授权决定是否实现；
8. 收集真实指标并最多进行三轮实施评估。

Skill 不应凭空补全“已验证”“已有用户反馈”等状态。脚本失败时应修复输入或向用户报告阻塞，不能手算一个看似合理的 winner 绕过校验。

## 16. 脚本模式与 CLI

从仓库根目录执行：

```powershell
$PIA = "skill/project-innovation-assistant/scripts/innovation_assistant.py"
python $PIA --help
```

### 16.1 初始化运行目录

```powershell
python $PIA init `
  --requirements "为独立开发者构建一个减少项目烂尾的本地工具" `
  --name "developer-finish-assistant" `
  --output-dir ".pia/developer-finish-assistant"
```

`init` 创建 `brief.json`、`candidates.template.json` 和 `generation-prompt.md`，不代表已经生成高质量创意。完成模型生成与两轮优化后，可将填好的模板另存为 `candidates.json`。已有三项初始化产物默认不覆盖；只有用户明确要求时才使用 `--force`。也可以用 `--requirements-file` 从 UTF-8 文本文件读取需求。

### 16.2 校验、评分和排序

补全二十项候选并完成两轮语义优化后执行：

```powershell
python $PIA rank `
  --brief ".pia/developer-finish-assistant/brief.json" `
  --candidates ".pia/developer-finish-assistant/candidates.json" `
  --output ".pia/developer-finish-assistant/decision.json" `
  --markdown ".pia/developer-finish-assistant/report.md"
```

`rank` 必须先验证 JSON、六维分数、20 项和 4×5 不变量，再计算排名。任何硬约束失败项都必须在输出中保留，但不得成为 winner。输入无效时脚本应以非零状态退出，并将可操作错误写入标准错误。

### 16.3 评估真实指标

```powershell
python $PIA evaluate `
  --decision ".pia/developer-finish-assistant/decision.json" `
  --metrics ".pia/developer-finish-assistant/metrics-round-1.json" `
  --output ".pia/developer-finish-assistant/iteration-round-1.json"
```

后续轮次可以带入上一轮历史：

```powershell
python $PIA evaluate `
  --decision ".pia/developer-finish-assistant/decision.json" `
  --metrics ".pia/developer-finish-assistant/metrics-round-2.json" `
  --history ".pia/developer-finish-assistant/iteration-round-1.json" `
  --output ".pia/developer-finish-assistant/iteration-round-2.json"
```

CLI 命令名和参数以脚本 `--help` 为运行时权威；本文与 v0.1 接口约定为 `init`、`rank`、`evaluate`。

## 18. 可观测性与审计

每次运行应该保存：

- `run_id`、时间、工具版本和 seed；
- 原始需求摘要与 brief 哈希；
- 候选数量和每组数量；
- 硬约束通过/失败数；
- Round 0/1/2 的输入输出哈希和变更摘要；
- 权重、基础分、每种调整和最终分；
- winner、用户覆写和覆写理由；
- 实现提交或产物引用；
- 真实指标来源与各轮建议。

日志不得写入密钥、访问令牌、私人对话、完整生产数据或不必要的个人信息。为了重现排序，保存规范化数值和脚本版本即可，不应过度收集上下文。

## 19. 测试策略

### 19.1 单元测试

- 权重归一化、非法权重与六维缺失；
- 分数、置信度、风险边界；
- `maximize` 与 `minimize` 指标目标判断；
- 硬约束门禁和 `unknown` 处理；
- 相似度与风险惩罚；
- 稳定排序和平局决胜；
- 历史轮次与最大迭代数。

### 19.2 协议测试

- 20 项、G1～G4 各 5 项通过；
- 19 项、21 项、重复 ID、缺组、6/4/5/5 必须失败；
- 某项约束失败时仍出现在 ranking，但 `eligible` 为假；
- 全部不合格时 winner 为空并给出阻塞原因；
- 未知字段不破坏兼容性，缺失必需字段产生清晰错误；
- JSON 与 Markdown 报告中的 winner、分数和淘汰原因一致。

### 19.3 场景测试

- 模糊需求：能记录假设而不是伪造事实；
- 极严约束：无合格候选时正确停止；
- 高创新低可行方案：不会仅凭创新性胜出；
- 五个近重复高分项：Top 5 不应被同一机制占满；
- 两轮优化：Round 0/1/2 可追溯，默认不出现 Round 3；
- 指标达标：`stop_on_target` 产生 `keep` 或 `stop` 的可解释建议；
- 护栏恶化：即使主指标达标，也不能无条件扩大实施。

### 19.4 端到端测试

使用固定 fixture 依次运行 `init`、填充候选、`rank`、`evaluate`。校验退出状态、文件存在性、JSON schema、二十项不变量、winner 资格和相同输入的确定性。测试不应访问付费服务或真实生产系统。

## 20. 验收标准

v0.1 发布前必须满足：

- [ ] Skill 能把一个项目需求转为结构化 brief；
- [ ] 默认候选严格为 20 个，且 G1～G4 各 5 个；
- [ ] 硬约束失败项不能成为 winner；
- [ ] 六维权重、分数、证据、置信度、风险和相似度调整可追溯；
- [ ] Round 1 和 Round 2 均有快照与变更理由；
- [ ] Top 5 有反方审查，Top 3 有可验证实验；
- [ ] 正常结果恰好一个 winner，无合格项时明确停止；
- [ ] `init`、`rank`、`evaluate` 的 CLI 示例可在 Python 3.11+ 运行；
- [ ] JSON 决策产物与 Markdown 报告一致；
- [ ] 完整流程能够输出 MVP、验收测试和指标计划；
- [ ] 实施评估遵守目标、护栏、最多轮次和停止条件；
- [ ] 不执行未授权外部副作用，不泄露敏感信息；
- [ ] 正向、负向和确定性测试全部通过。

## 21. 风险与安全

| 风险 | 影响 | 控制 |
| --- | --- | --- |
| 需求误解 | 二十项都偏离真正问题 | 保留原文、显式假设、winner 前复述目标与非目标 |
| 创意同质化 | 虚假的选择丰富度 | 固定 4×5 探索组合、相似度处理、一对一替换 |
| 模型自我确认 | 高估早期偏好 | Top 5 强制反方审查、证据/置信度分离 |
| 评分游戏 | 为偏好方案事后调权 | 权重先于评分冻结，改权重产生新版本 |
| 伪造证据 | 决策建立在不存在的数据上 | 证据类型、来源、待验证标记；禁止虚构引用 |
| 指标代理失效 | 提升数字却伤害用户 | 主指标与护栏指标并用，人工审查因果关系 |
| 提示注入 | 外部文本诱导越权 | 外部内容按不可信数据处理，不作为系统指令 |
| 敏感信息泄露 | 凭据或个人数据进入产物 | 最小化上下文、脱敏、日志过滤、提交前审查 |
| 破坏性实现 | 删除数据或影响生产 | 小步提交、备份/回滚、真实副作用前获得授权 |
| 自动化过度 | 脚本结论被误当事实 | 保留业务判断边界、用户覆写与理由 |
| 无限迭代 | 浪费预算且无法决策 | 方案优化固定两轮，实施评估默认最多三轮 |

## 22. 故障处理

| 故障 | 处理方式 |
| --- | --- |
| Brief 缺少关键约束 | 停止 winner 选择，向用户询问会改变方向的最小问题集。 |
| 候选不是 20 项或分组不合法 | `rank` 非零退出，修复输入后重新运行，不做部分排名。 |
| 候选 JSON 无效 | 报告文件、字段和错误位置；不得静默使用默认值覆盖错误。 |
| 所有候选不合格 | 输出约束冲突摘要，建议放宽条件或重新生成，不选择 winner。 |
| Top 3 依赖互相矛盾的未知事实 | 暂停并设计信息增益最高的验证，不猜测结论。 |
| 指标文件缺失或数据质量差 | 不生成成功结论；说明缺失项和可接受的数据采集方式。 |
| 实现测试失败 | 保留失败输出，修复或回滚；不得进入“已验证”状态。 |
| 发生安全/合规疑问 | 立即停止相关执行，将决策交还用户或专业审查者。 |

## 23. 路线图

## 24. 最小操作清单

一次合格运行可用下面的清单复核：

1. 冻结 brief、权重、硬约束和成功指标；
2. 生成 G1～G4 各五项，合计恰好二十项；
3. 执行硬约束门禁和首次评分；
4. 完成 Round 1：覆盖、去重、约束修复、Top 5 反方审查；
5. 完成 Round 2：Top 3 实验化、落地压力测试、最终重排；
6. 通过脚本校验并生成 `decision.json` 与报告；
7. 只从合格项中选一个 winner，或在无合格项时明确停止；
8. 获得实现授权后交付 MVP 和测试；
9. 用真实指标执行评估，输出 keep/iterate/pivot/stop；
10. 在目标达成、护栏失败、预算耗尽或轮次上限时停止。

这十步共同构成项目创新助手的最小闭环；缺失“二十项完整候选、硬约束门禁、两轮优化、可追溯评分、明确停止条件”中的任何一项，都不能称为完成了本手册定义的 PIA 流程。
